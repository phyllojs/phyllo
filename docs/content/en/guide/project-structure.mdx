# Project structure \{#project-structure\}

After you create a project, the site contains a content directory, site configuration, a theme and dependency declarations. This page explains what each directory and file is for.

## Directory overview \{#overview\}

A site that uses a custom theme looks like this:

```text
my-site/
├── .phyllo/
│   └── types.d.ts
├── content/
│   ├── index.mdx
│   └── getting-started.mdx
├── public/
├── themes/
│   └── my-theme/
│       ├── src/
│       │   └── index.tsx
│       ├── package.json
│       └── tsconfig.json
├── bun.lock
├── package.json
├── phyllo.config.ts
└── tsconfig.json
```

`content/` and the configuration file are required. Keep `public/` and `themes/` only when you need them. The tool generates `.phyllo/`, and you create `public/` yourself when needed. Neither appears right after initialization.

Day-to-day writing only involves `content/` and `phyllo.config.ts`. The other files handle dependencies, types and build output.

## The content directory \{#content\}

`content/` holds every article in the site. Each file maps to a page. For the address rules, see [Pages and routing](./routing.mdx).

You can keep articles in a single directory, or organize them into sections in subdirectories:

```text
content/
├── guide/
│   ├── configuration.mdx
│   └── installation.mdx
├── getting-started.mdx
└── index.mdx
```

When you want to use components in articles, put the component files in `content/components/` and import them by relative path. `.tsx` components don't generate pages. Put `.mdx` snippets that you reuse across articles in directories that start with `.`, so they aren't collected as pages.

Directory symlinks inside `content/` are followed. Articles in a linked directory get page addresses from their path under `content/`, and relative links and assets in their bodies resolve against the same logical path:

- Directories that start with `.` are skipped when scanning for pages, but MDX snippets inside them can still be imported.
- Symlinks that point to files aren't collected, so the same file doesn't produce duplicate pages.
- The same real directory can only appear through one link path. Multiple links make page addresses ambiguous, so the build fails with an error.
- When the link target is inside the site directory, the dev server updates the page on save. Targets outside the site directory aren't watched, so you need to restart the dev server.

## The public directory \{#public\}

`public/` holds static files that don't need build processing, such as the tab icon, fonts and other images the site references. Files in this directory are copied to the output root as they are, so `public/favicon.svg` is served at `/favicon.svg`. This directory isn't created automatically. Create it when you have files like these to add.

Images referenced from articles are better placed in `content/`. The build generates hashed files and rewrites the references. For the difference between the two approaches, see [Links and assets](./links-and-assets.mdx).

## The themes directory \{#themes\}

When you choose a custom theme while creating a site, the tool generates the matching theme directory under `themes/`. Themes exist as packages, and the project references one by name.

Local theme source is stored in the project, so you can modify it yourself. If you don't need a custom look, you can switch to a theme published on npm, and then you don't need to keep this directory. For the difference between the two, see [Theme overview](../themes/overview.mdx).

## The .phyllo directory \{#phyllo\}

`.phyllo/` holds files generated by the tool. It appears after you first run the dev server, build, or sync command:

- `types.d.ts` is generated from your content and gives editors type hints for article addresses and the content directory.
- `bunfig.toml` is written on the first dev run. It tells Bun to load the dev server plugin.
- `dev/` and `build/` store intermediate files for dev and build.

The tool maintains these files, so you don't need to edit them by hand. They update automatically the next time you run the dev server or a build.

## Configuration files \{#config-files\}

| File               | Purpose                                                                              |
| ------------------ | ------------------------------------------------------------------------------------ |
| `phyllo.config.ts` | Common settings such as site name, description, theme, HTML language and search      |
| `package.json`     | Dependency declarations and the `dev`, `build` and `sync` scripts                    |
| `bun.lock`         | Locks dependency versions so installs are reproducible                               |
| `tsconfig.json`    | TypeScript configuration, including the content directory and generated declarations |

In the root directory, `phyllo.config.ts` is the only file you edit by hand. When dependencies change, Bun writes `package.json` and `bun.lock`, so you don't need to change them yourself.

## Version control \{#version-control\}

Commit these to your repository:

- Articles and components in `content/`.
- Static assets in `public/`.
- Local theme source in `themes/`.
- `phyllo.config.ts`, `package.json`, `bun.lock` and `tsconfig.json`.

`node_modules/`, `dist/` and `.phyllo/` don't need to be committed. The `.gitignore` generated by the init tool already covers these rules. `bun.lock` does need to be committed, because hosting platforms install dependencies from it.

Now that you know what each directory is for, continue with [Site configuration](./configuration.mdx).
